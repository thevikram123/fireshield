# Functional MVP architecture

## Chosen direction

- **Flutter remains the app UI.** Keep service/repository interfaces portable for a later React client.
- **Cloudflare Worker remains the AI trust boundary.** Groq keys, model limits and NBCS retrieval stay server-side.
- **Supabase provides identity and persistence.** Auth identifies users; Postgres stores assessments and facts; private Storage holds source evidence and generated artifacts; RLS enforces organisation membership.
- **A Python container runs geometry/CV jobs.** It owns PDF rasterisation, deterministic floor-plan extraction, bounded Qwen topology correction and DXF/overlay generation.
- **PDF reports are generated from stored assessment records.** Flutter's `pdf`/`printing` packages are the preferred MVP path for cross-platform download/share; a server-side ReportLab renderer can be added for scheduled/batch reports.

## Working feature map

| Product function | Existing capability to reuse | Additional tool/service |
|---|---|---|
| Free-form safety chatbot | GPT-OSS + NBCS KV graph | Persist conversations only if users opt in |
| Site photo assessment | image_picker + CLIPSeg + Qwen + GPT-OSS | Supabase Storage + assessment records |
| Floor-plan image/PDF | OpenCV/CubiCasa pipeline + Qwen | Container job API + private Storage |
| DXF/JSON/overlay | ezdxf + existing semantic schema | Artifact metadata + signed downloads |
| Compliance findings | GPT-OSS tool calls into NBCS graph | Reviewer acceptance/edit state |
| Analytics dashboards | Existing charts and typed models | SQL view over completed assessments; no LLM-calculated KPIs |
| Narrative insights | GPT-OSS | Feed only deterministic metrics and cited findings |
| PDF export | Existing assessment model | Flutter `pdf` + `printing`, render-and-verify tests |
| Real users/roles | Current role UI | Supabase Auth + profiles + organisation memberships |
| Long-running plan jobs | None | Cloudflare Container; Queue/Workflow only if synchronous jobs exceed demo latency |
| Error monitoring | None | Sentry later; not required for first showcase |
| Product usage analytics | None | PostHog later; separate from fire-safety analytics |

## Evidence lifecycle

1. Authenticated user creates a site or plan assessment.
2. Original files upload to a private organisation-scoped path.
3. A model run records provider, model, purpose, input artifact IDs, latency and status.
4. CLIPSeg/Qwen detections and GPT-OSS findings are stored separately from originals.
5. Reviewer accepts, rejects or edits machine findings.
6. Deterministic scoring writes the assessment score and completion timestamp.
7. PDF/DXF/JSON/overlay outputs become versioned artifacts.
8. Dashboard views aggregate completed assessments without re-running AI.

## Minimum configuration needed to link Supabase

1. Create one Supabase project.
2. Apply `supabase/migrations/202608150001_functional_mvp.sql`.
3. Create a private bucket named `assessment-artifacts` and its organisation-scoped policies.
4. Add Flutter build defines for `SUPABASE_URL` and the publishable key. The service-role key must never enter Flutter.
5. Add `supabase_flutter`, replace demo email login with Auth, and keep Quick Login behind an explicit showcase-only switch.
6. Forward the signed-in JWT to the Worker; the Worker validates identity before accepting stored assessment work.

## PDF report contents

- Cover: facility, assessment type/date, reviewer and overall score.
- Executive summary generated by GPT-OSS from already-stored facts.
- Deterministic score breakdown and trend chart.
- Evidence thumbnails with model/source/confidence and reviewer state.
- Findings table with severity, observed/required, decision and NBCS page citation.
- Plan appendix with overlay preview and links/checksums for DXF and JSON.
- Methodology, model versions, limitations and statutory disclaimer.

## What is not required for the first showcase

- Full organisation billing or invitations.
- Government notice/escalation workflow.
- Push notifications and email automation.
- A data warehouse or BI platform.
- A separate vector database; the current NBCS index is sufficient for MVP grounding.
